# badcase 拆解与效果优化记录

> 本文记录 RAG 问答系统迭代过程中发现的典型 badcase，以及完整的"现象 → 定位 → 方案 → 验证"过程。
> 方法：收集真实使用中的失败案例 → 先看数据定位根因 → 小步修改 → 回归验证 → 沉淀经验。

---

## 案例 1：检索答非所问——无关段落排名第一

**现象**：提问"年假有几天？"，检索到的 top-1 是社保公积金段落（与问题无关），真正含答案的"年假"段落只排第二。文档少时答案侥幸还在 top-3 内；文档一旦变多，答案段落会被挤出 top-3，生成环节看不到正确资料，只能凭模型记忆"编"答案——答对了是运气，答错了就是一本正经的幻觉。

**定位**：
1. 调出问题向量与全部段落向量的余弦相似度分数，确认排序确实错乱；
2. 检查含答案的段落内容，发现"年假"内容只占该块约 1/10，其余是离职补偿等内容——块的语义被稀释；
3. 根因：embedding 相似度只能衡量"整体语义像不像"，无法判断"该段能否真正回答问题"；且问题很短（5 个字），信号弱。

**方案**：将"一步检索"改为**两段式检索**：
- ① 向量粗筛 top-6：宁可多拿不能漏，保证召回率；
- ② LLM 精排 top-3：采用 RankGPT 思路（逐段打 0-10 分并给理由，最后输出排序编号列表），按"能否回答问题"重新排序，保证精度。

**验证**：用同一问题回归验证，含答案段落重新回到前列。后续多轮测试中，两段式检索在多个问题上均能纠正或确认排序。

**遗留**：LLM 精排偶尔也会选进无关段落（如给"年终奖"问题选入"年假申请流程"），且每次精排多一次 LLM 调用。下一步计划替换为专门训练的 rerank 模型（bge-reranker）。

## 案例 2：交互体验——页面长时间无响应

**现象**：网页版提问后，参考段落与回答要等十几秒才一起出现，用户对着空白页面干等；回答也感觉是"一次性全部弹出"，没有流式打字机效果。

**定位**：检查服务端执行顺序，发现所有步骤是串行阻塞的——向量检索 → LLM 重排序（最慢，约 10-30 秒）→ 生成。重排序跑完之前，服务器没有向前端推送任何数据。前端从发起请求到收到第一个字节的延迟，等于全部步骤耗时之和。

**方案**：重构为"边做边发"的 SSE 事件流：
- 收到请求后立即推送状态消息；
- 向量粗筛是本地计算（毫秒级），完成后立刻把 top-6 候选推给前端；
- 重排序期间推送"正在重排序"状态，完成后推送精排结果 top-3；
- 生成阶段用 stream=True 流式输出，模型每生成一个 token 就推送一个。

**验证**：页面首屏反馈从"十几秒无响应"优化到"1 秒内看到候选段落"；生成阶段逐字输出，实现打字机效果。

## 案例 3：交互体验——思考过程状态残留

**现象**：任务全部完成后，思考过程区域仍显示多条"正在……"的行（正在向量检索、正在重排序……），与"✓ 完成"的行混在一起，用户无法一眼看出当前状态。

**定位**：前端把"开始做"和"做完了"实现为两条独立消息，各追加一行 DOM。任务结束后，"开始做"的行从未被移除或更新，属于状态展示的生命周期管理缺失。

**方案**：将每个阶段改为"单行就地变身"——开始阶段显示"正在……"（带动态省略号动画），完成事件到达时**原地替换**该行文本为"✓ 完成 + 耗时"，不新增行。

**验证**：任务完成后思考区域只保留 3 行完成记录（检索/重排/生成），状态一目了然。

## 方法论总结

1. **先看数据再改**：badcase 出现后先调出中间结果（相似度分数、段落内容、执行顺序）定位根因，不凭感觉猜；
2. **小步修改、回归验证**：每次只改一个变量，用同一问题集回归，确认修复且没有引入新问题；
3. **两类 badcase 分开治理**：效果类（检索/生成质量）靠算法方案（两段式检索、rerank）；体验类（响应/状态）靠工程方案（SSE、事件驱动 UI）；
4. **沉淀评测集**：典型的失败问题应沉淀为回归用例，防止未来改动悄悄破坏已修复的 case（计划引入 RAGAS 自动化评测）。
